# Miyabi 媒体库整理与 115 扫描方案

状态：讨论方案，尚未实现或完成部署验收。本文只描述项目实现与改造边界，不记录账号、令牌、媒体清单等敏感信息。

## 目标与不变约束

- 从 115 的若干平级子目录中分别选择入库范围；共同父目录可能包含大量无关资源，不能通过挂载父目录代替精确选择。
- 首次扫描、后续扫描和刮削尽量控制 115 请求量；不承诺完全规避服务端风控。
- **不移动、不重命名、不复制 115 原文件。** 已刮削影片的分类、演员关联和媒体库重导出应仅使用 Miyabi 数据库中的影片资料与文件索引，以及本地缓存的图片。
- 给 Jellyfin／Emby 的每部影片只导出一套 STRM、NFO 和图片。影片可以关联多位演员；两位主演各自的演员卡片都应能关联同一部影片，而不是在两个演员文件夹各复制一份影片。
- 将“远程发现或校验文件”“外部资料刮削”“本地导出与媒体服务器通知”区分为独立操作；不能把重新分类隐式做成 115 重扫。

## 当前实现与访问 115 的范围

| 操作 | 当前行为 | 是否访问 115 |
| --- | --- | --- |
| 挂载媒体目录 | 一次只保存一个目录，替换挂载后触发新扫描 | 是：校验账号和目录 |
| 全量扫描／普通重扫 | 从挂载目录逐层遍历所有子目录，目录列表按每页 100 项读取；记录检查点，扫描后按来源对账 | 是：重扫仍会重新遍历 |
| 定向扫描 | 仅针对指定文件或子目录，但仍查询目标与相关目录 | 是 |
| 单片刮削与发布 | 获取或复用资料；导出前查询影片所在目录，并逐个查询视频信息以验证位置 | 是；即使资料已缓存，现有发布路径仍需校验 115 文件 |
| 已保存资料的导出修复 | 用已索引文件 ID、保存的 NFO 资料和本地图片缓存生成附件 | 导出函数本身不访问 115；当前主要由扫描后的对账流程调用 |
| 播放 STRM | 播放地址包含 Miyabi 的文件 ID 路由，播放时解析 115 播放或下载地址 | 是，播放不属于离线分类 |

扫描器对**每次目录分页请求**额外等待约 350～499 毫秒；115 客户端共享请求限制为至少间隔 250 毫秒、最多两个在途请求，并在 `Retry-After` 指示后等待，对部分失败重试。这些限制不等于整个工作流每个请求都有 350 毫秒间隔：刮削中的目录查询和逐文件校验仅受客户端共享限制。实际请求数取决于目录和分页数量、视频数量及并发的其他功能；无法从代码推断 115 的安全阈值，更不能保证不触发风控。

关键位置：`internal/drive/mount.go`、`internal/library/scan/walker.go`、`internal/drive/session.go`、`internal/pan/client.go`、`internal/library/scrape/scrape.go`、`internal/library/scrape/publish.go`。

## 方案一：选择多个平级目录入库

将单个挂载目录改为同一账号下的多个**明确选中的扫描根目录**，列表展示所选范围，并允许单独添加、移除与扫描。只遍历每个所选子目录及其后代，不扫描共同父目录的其他分支；首次扫描与后续按根目录的扫描应分别排队并控制请求节奏，避免多任务叠加请求。保留每个根目录的进度和恢复点。

索引、任务和清理须以账号及所选扫描根目录标识隔离：扫描 A 未发现的文件不能导致 B 的索引或导出被删除；跨目录属于同一影片时，还应依据全部仍有效的文件引用判断是否清理该影片。目录重叠、取消挂载、跨目录移动与重新挂载的语义需要明确，并通过回归测试覆盖。现有 `database.LibraryFiles` 和扫描对账以单一来源为核心，不能只把前端选择器改成多选。

此前按“同一账号、多个平级根目录”的收窄场景估算约 **4～8 个开发日**，不含大目录现场验收；这是粗估而非承诺。

## 方案二：离线归类与演员卡片

### 已有资料与目标展示

刮削结果已保存影片、演员及标签关系，并在 NFO 中写入多位演员、标签和类型；当前导出路径为 `<导出根目录>/<番号前缀>/<番号>/`。扫描初期主要依据文件名识别番号，完整演员与类别通常要等刮削完成后才能使用。因此“归类”应以**已刮削数据**为输入，而不是在读取 115 目录时推断。

一部影片可以关联多位演员。在 Jellyfin／Emby 中期望的是**一条影片记录被多张演员卡片引用**：保留单份导出，并依靠 NFO 演员字段建立关系，不按演员复制多套 STRM。当前模型有参演演员列表，但没有可靠的“主演／配角”标记；若要只在主演卡片出现而不展示其他参演者，必须另行确定主演来源、顺序或人工修订规则。若期望所有参演者的卡片都能看到该片，现有多演员数据结构已具备基础，最终表现仍需目标服务器验证。

类别优先使用 NFO 的类型／标签供媒体服务器筛选。只有确认需要按文件夹浏览时，才考虑可配置的**单一目录归类**（例如类别／番号、未分类／番号），明确多类别的优先级；同一影片同时复制到多个类别目录可能导致重复影片和播放进度分叉，不作为默认方案。

### 独立的离线重导出任务

新增一个与扫描／刮削分离的“从已有资料重建导出”入口：

1. 从本地数据库分页读取已完成刮削的影片、文件 ID、演员／标签关联及已保存的 NFO 资料，读取本地缓存图片；缺资料或缓存损坏时报告失败或跳过，不自动回退到 115 扫描或重新刮削。
2. 依据稳定的路径规则只生成一套影片附件；改规则前验证安全文件名、路径冲突及不同影片同编号的处理。只清理 Miyabi 确认生成的旧附件，不触碰用户手工文件。
3. 当导出路径变更时，同步更新重扫修复、旧影片删除、番号更正、字幕落点及媒体更新通知；对旧路径和新路径均发通知，避免媒体服务器残留或重复入库。尽量保持任务可重试、重复执行结果一致，并保留失败明细。
4. 为本操作建立明确的**零 115 API 调用**边界及自动化测试：不创建 115 会话，不调用 `List`、`Info`、`Read`、`PlayURL` 等方法。手动扫描、下载入库、重新刮削及实际播放继续遵循各自的远程请求流程。

现有 `ExportLocalMovie` 可复用，但它目前主要在扫描对账中调用；不能把“点重新分类”直接接到 `StartRebuild` 或 `StartScan`。关键位置：`internal/library/scrape/export.go`、`internal/library/scan/reconcile.go`、`internal/library/scrape/rename_export.go`、`internal/library/scrape/publish.go`、`internal/nfo/movie.go`。

单一目录归类连同配置、迁移和回归测试此前粗估 **3～6 个开发日**。若只要求多演员卡片关联且 NFO 已能被媒体服务器正确读取，优先验证现有行为，未必需要修改目录布局；精确区分“主演”则另计。

## Jellyfin／Emby 更新问题：先定位再改造

当前媒体服务连接测试只请求 `/System/Info`，不能证明库更新已成功。刮削发布后，Miyabi 导出 STRM／NFO／图片，并通过 Emby 风格接口 `POST /Library/Media/Updated` 发增量通知；通知是否被 Jellyfin 有效处理、容器路径是否正确映射、媒体库是否覆盖导出目录，尚无现场证据。不能把“通知已发送”直接等同于“媒体库已更新”。

按顺序验证：导出附件确实存在且内容有效；Miyabi 与媒体服务器容器看到同一份目录，媒体服务器库包含该路径；对比手动扫描后的结果；检查通知记录、接口响应与媒体服务器日志，再决定是修路径配置、补通知诊断，还是增加 Jellyfin 专用刷新适配。此前条件性粗估：现场排查 **半天～1 天**；简单路径／配置修复 **半天～2 天**；确需专用适配约 **2～5 天**。在这个问题解决前，不能承诺演员卡片会即时更新。

## 内置播放的探索边界

已有 `/api/strm/play/:fileID` 能为 STRM 解析播放地址，不能等同于已有网页播放器。若以后增加 Miyabi 内置播放，需验证登录与播放鉴权、URL 时效、浏览器支持的格式、Range／跨域及必要时的转码或 HLS。播放必然会访问 115 或其媒体 CDN，因此不能纳入“离线归类零请求”的保证；当前不作为上述入库改造的前置任务。

## 实施与验收顺序

1. **先排通 Jellyfin 更新链路**，用一部已有影片确认媒体路径、NFO 演员解析及演员卡片表现；不要把连接测试当成验收。
2. 为现有 115 请求建立可观测统计与风控错误记录（不记录令牌／敏感路径）；在受控样本目录测算分页、逐文件校验及重试量，不在巨大父目录上直接压测。
3. 如需扩大覆盖范围，先实现多个明确扫描根目录及严格的跨来源清理隔离，再以少量平级目录验收；并发与限速应以**同一 115 客户端／账号的总体负载**为准。
4. 实现并测试独立的离线重导出；分别验收双演员同片单份入库、归类规则变更、旧路径清理、重试及整个任务零 115 请求。
5. 单独评估网页播放，不使其改变扫描和离线导出边界。
